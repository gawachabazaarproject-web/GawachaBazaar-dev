# Gawacha Bazaar Database Specification: Version 5 — Packaging & Labeling

This document defines the database architecture and technical specifications for **Phase 5: Packaging & Labeling** of the Gawacha Bazaar platform.

---

## 1. Business Context & Physical Process Flow

Gawacha Bazaar delivers authentic village farm produce directly to consumers. The journey from field to doorstep follows an unbroken physical and operational flow:

```text
Village Farm (Grower)
    │
    ▼
Harvest (Batch Created)
    │
    ▼
Collection (Aggregation)
    │
    ▼
Sorting & Grading (Quality Inspection)
    │
    ▼
Gawacha Bazaar Hub (Inventory Storage)
    │
    ▼
Packaging & Labeling (Commercial Preparation - Phase 5)
    │
    ▼
Delivery (Logistics Dispatch)
    │
    ▼
Nagpur City (Urban Distribution)
    │
    ▼
Customer Home
```

### Clarification of "Preparation"
In the Gawacha Bazaar operating model, "Preparation" refers strictly to **final commercial preparation**:
- Packing bulk or graded produce into sellable retail package sizes (e.g., 500g trays, 1kg bags, 5kg mesh sacks).
- Affixing identifying labels and branding.

It explicitly does **not** mean culinary food processing, cooking, chemical transformation, manufacturing recipes, bills of materials (BOM), production yield tracking, or industrial manufacturing workflows. Phase 5 is therefore designated as **Packaging & Labeling**.

## 2. Core Architectural & Domain Invariants

### 2.1 Batch Identity & Traceability Preservation
1. **Packaging Does Not Create a Batch**:
   Harvest batches (`batches`) represent agricultural origin, soil conditions, farmer identity, and harvest date. Packaging is a commercial packaging step, not an agricultural harvest event. Creating new batches during packaging would break traceability to the origin farm.
2. **One Output Inventory Lot = One Source Batch**:
   An `inventory_lot` is uniquely defined by `(batch_id, variant_id, location_id)`. Because an inventory lot belongs to exactly one `Batch`, an output inventory lot must never mix source batches. If a packaging operation packages produce originating from multiple batches (e.g., Batch A and Batch B), the operation must output separate inventory lots for Batch A and Batch B.

### 2.2 Operational Balance Reuse (`inventory_lots`)
The Phase 4 inventory model dictates that an inventory lot represents the current physical balance for `(batch_id, variant_id, location_id)` with `UNIQUE(batch_id, variant_id, location_id)`.
- When a packaging operation finishes, its output records (`packaging_outputs`) point directly to the operational `inventory_lot` receiving the packaged goods.
- If an inventory lot for that specific `(batch_id, variant_id, location_id)` already exists at the facility, it is reused.
- Duplicate inventory lots are never created for the same combination.
- `packaging_operation_id` is **not** added to `inventory_lots`.

### 2.3 Package Count & Total Quantity (No `quantity_per_package`)
Packaged output is defined strictly by:
- `package_count` (INTEGER > 0): The number of physical packages prepared.
- `total_quantity` (NUMERIC(12, 3) > 0): The total mass or volume of produce packaged.

`quantity_per_package` is **intentionally omitted** because package size is already explicitly modeled by the selected `ProductVariant` (which specifies packaging unit, size, and SKU). Redundant columns that can drift out of sync are avoided.

### 2.4 Multi-Input & Multi-Output Packaging Operations
- **Many-to-Many Operational Capability**: A single packaging operation can consume multiple input inventory lots (e.g., combining different bulk lots or grading fractions of the same produce) and produce multiple packaged output lots (e.g., packing 500g punnets and 1kg boxes in the same run).
- **Multiple Inputs for Same Lot**: Multiple `packaging_inputs` records may reference the same `inventory_lot_id` within a single operation (e.g., staged consumption increments).

### 2.5 Append-Oriented Nature
Packaging inputs and outputs are recorded as operational ledger entries. While database-level immutability triggers are avoided, the schema is designed for append-oriented usage without `updated_at` columns on input/output records.

### 2.6 Deferred Label Management Schema
Detailed regulatory, statutory, and nutritional label specifications remain under active business review. No speculative label tables, label templates, or print-job tracking schemas have been introduced at this stage.

## 3. Detailed Table Specifications

### 3.1 `packaging_operations`
Represents an authorized packaging and labeling run at a physical facility.

| Column | Type | Nullable | Default | Description |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `BIGINT` | `NO` | `GENERATED BY DEFAULT AS IDENTITY` | Primary key |
| `packaging_code` | `VARCHAR(100)` | `NO` | — | Unique operation reference (e.g., `PKG-2026-0001`) |
| `name` | `VARCHAR(150)` | `NO` | — | Operation title (e.g., "Nagpur Orange Festive Gift Packaging") |
| `location_id` | `BIGINT` | `NO` | — | FK to `inventory_locations.id` where packaging occurs |
| `status` | `VARCHAR(30)` | `NO` | — | Status (`DRAFT`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`) |
| `started_at` | `TIMESTAMPTZ` | `NO` | — | Timestamp when operation started |
| `completed_at` | `TIMESTAMPTZ` | `YES` | `NULL` | Timestamp when operation finished |
| `performed_by_user_id` | `BIGINT` | `NO` | — | FK to `users.id` (operator / supervisor) |
| `remarks` | `TEXT` | `YES` | `NULL` | Operational notes or instructions |
| `created_at` | `TIMESTAMPTZ` | `NO` | `now()` | Record creation timestamp |
| `updated_at` | `TIMESTAMPTZ` | `NO` | `now()` | Record update timestamp |

#### Constraints & Indexes
- **Primary Key**: `PRIMARY KEY (id)`
- **Unique Constraint**: `uq_packaging_operations_packaging_code` ON `(packaging_code)`
- **Foreign Keys**:
  - `fk_packaging_operations_location_id_inventory_locations` FOREIGN KEY (`location_id`) REFERENCES `inventory_locations(id)` ON DELETE RESTRICT
  - `fk_packaging_operations_performed_by_user_id_users` FOREIGN KEY (`performed_by_user_id`) REFERENCES `users(id)` ON DELETE RESTRICT
- **Check Constraints**:
  - `ck_packaging_operations_status` CHECK `status IN ('DRAFT', 'IN_PROGRESS', 'COMPLETED', 'CANCELLED')`
  - `ck_packaging_operations_completed_at` CHECK `completed_at IS NULL OR completed_at >= started_at`
- **Indexes**:
  - `ix_packaging_operations_location_id` ON `(location_id)`
  - `ix_packaging_operations_status` ON `(status)`
  - `ix_packaging_operations_started_at` ON `(started_at)`

### 3.2 `packaging_inputs`
Records the specific inventory lots and quantities consumed during a packaging operation.

| Column | Type | Nullable | Default | Description |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `BIGINT` | `NO` | `GENERATED BY DEFAULT AS IDENTITY` | Primary key |
| `packaging_operation_id` | `BIGINT` | `NO` | — | FK to `packaging_operations.id` |
| `inventory_lot_id` | `BIGINT` | `NO` | — | FK to `inventory_lots.id` (source stock consumed) |
| `quantity` | `NUMERIC(12,3)`| `NO` | — | Consumed stock quantity (strictly positive) |
| `created_at` | `TIMESTAMPTZ` | `NO` | `now()` | Record creation timestamp |

#### Constraints & Indexes
- **Primary Key**: `PRIMARY KEY (id)`
- **Foreign Keys**:
  - `fk_packaging_inputs_operation_id_packaging_operations` FOREIGN KEY (`packaging_operation_id`) REFERENCES `packaging_operations(id)` ON DELETE RESTRICT
  - `fk_packaging_inputs_inventory_lot_id_inventory_lots` FOREIGN KEY (`inventory_lot_id`) REFERENCES `inventory_lots(id)` ON DELETE RESTRICT
- **Check Constraints**:
  - `ck_packaging_inputs_quantity` CHECK `quantity > 0`
- **Indexes**:
  - `ix_packaging_inputs_packaging_operation_id` ON `(packaging_operation_id)`
  - `ix_packaging_inputs_inventory_lot_id` ON `(inventory_lot_id)`

Records the packaged products output from the operation, linked directly to receiving inventory lots.

| Column | Type | Nullable | Default | Description |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `BIGINT` | `NO` | `GENERATED BY DEFAULT AS IDENTITY` | Primary key |
| `packaging_operation_id` | `BIGINT` | `NO` | — | FK to `packaging_operations.id` |
| `inventory_lot_id` | `BIGINT` | `NO` | — | FK to `inventory_lots.id` (receiving packaged stock) |
| `package_count` | `INTEGER` | `NO` | — | Number of retail packaging units produced |
| `total_quantity` | `NUMERIC(12,3)`| `NO` | — | Total packaged quantity |
| `created_at` | `TIMESTAMPTZ` | `NO` | `now()` | Record creation timestamp |

#### Constraints & Indexes
- **Primary Key**: `PRIMARY KEY (id)`
- **Foreign Keys**:
  - `fk_packaging_outputs_operation_id_packaging_operations` FOREIGN KEY (`packaging_operation_id`) REFERENCES `packaging_operations(id)` ON DELETE RESTRICT
  - `fk_packaging_outputs_inventory_lot_id_inventory_lots` FOREIGN KEY (`inventory_lot_id`) REFERENCES `inventory_lots(id)` ON DELETE RESTRICT
- **Check Constraints**:
  - `ck_packaging_outputs_package_count` CHECK `package_count > 0`
  - `ck_packaging_outputs_total_quantity` CHECK `total_quantity > 0`
- **Indexes**:
  - `ix_packaging_outputs_packaging_operation_id` ON `(packaging_operation_id)`
  - `ix_packaging_outputs_inventory_lot_id` ON `(inventory_lot_id)`

## 5. Scope Control & Explicit Exclusions

The following concepts are intentionally excluded from Phase 5:
- **No Food Processing / Cooking / Manufacturing**: No recipe models, Bills of Materials (BOM), transformation steps, cooking yield calculations, or intermediate production phases.
- **No Package-Level Tracking**: Individual physical package identifiers, barcodes, RFID tags, or package serial numbers are not modeled.
- **No Label Management Subsystem**: No label templates, dynamic label design fields, label printer jobs, or regulatory text storage.
- **No Automatic Stock Deduction Triggers**: Stock movements and inventory lot quantity synchronization will be executed atomically by a future application service layer.
- **No Unit Conversion Engine**: Input/output quantity reconciliation logic will be handled by application business logic.
- **No Commercial / Transactional Tables**: Orders, order items, carts, payments, delivery schedules, promotions, and customer reviews belong to downstream domains.
