# Phase 8 — Production Authentication Architecture

## 1. Executive Summary

Phase 8 establishes the production authentication foundation for the Gawacha Bazaar FastAPI backend service. Building upon the 25-table database foundation (Phases 1–7) and the modular-monolith application layer (Phase 7 checkpoint), Phase 8 implements server-side session management, cryptographically hardened password hashing, short-lived JWT access tokens, opaque high-entropy refresh tokens, and strict account status enforcement.

---

## 2. Database Schema (`auth_sessions`)

To support server-side session state and refresh token revocation, Phase 8 introduces exactly **one new database table** via Alembic migration `4d9160d1bcc6`:

```
Table: auth_sessions
├── id                 : BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
├── user_id            : BIGINT NOT NULL FK -> users.id ON DELETE CASCADE (indexed)
├── refresh_token_hash : TEXT NOT NULL UNIQUE
├── expires_at         : TIMESTAMPTZ NOT NULL (indexed)
├── created_at         : TIMESTAMPTZ NOT NULL DEFAULT now()
├── last_used_at       : TIMESTAMPTZ NULL
├── revoked_at         : TIMESTAMPTZ NULL (indexed)
├── device_name        : VARCHAR(150) NULL
├── ip_address         : VARCHAR(45) NULL
└── user_agent         : TEXT NULL
```

### Deletion Policy Rationale
Unlike financial or inventory ledgers where records are preserved with `RESTRICT`, authentication sessions have no independent business meaning once a user account is deleted. Thus, `users -> auth_sessions` uses `ON DELETE CASCADE`.

## 3. Token & Session Architecture

### Access Tokens (JWT)
- **Lifetime**: Short-lived, 15 minutes (`ACCESS_TOKEN_EXPIRE_MINUTES = 15`).
- **Algorithm**: `HS256` signed using `JWT_SECRET_KEY`.
- **Claims Architecture**:
  - `sub`: User ID as string (e.g., `"123"`).
  - `sid`: Database `auth_sessions.id` linking the access token to the active session.
  - `iat`: UTC issued-at timestamp.
  - `exp`: UTC expiration timestamp (~15 minutes).
  - `jti`: Unique UUID4 hex identifier.
  - `type`: Explicitly `"access"`.
  - `iss`: Configured issuer (`"gawachabazaar"`).
  - `aud`: Configured audience (`"gawachabazaar:api"`).
- **Claim Sanitization**: Passwords, hashes, emails, phone numbers, or role trees are **strictly prohibited** in the access token.

### Refresh Tokens (Opaque High-Entropy)
- **Entropy**: Cryptographically secure string generated using `secrets.token_urlsafe(48)` (~384 bits entropy).
- **Storage**: Raw refresh tokens are **never** stored in PostgreSQL, never logged, and never included in error responses. Only the SHA-256 digest (`hash_refresh_token`) is stored in `auth_sessions.refresh_token_hash`.
- **Why SHA-256**: Unlike low-entropy human passwords (which require slow, memory-hard Argon2id), a 384-bit random opaque token has sufficient entropy to make brute-force preimage attacks mathematically infeasible, while avoiding high CPU costs on high-throughput refresh paths.

### Absolute Session Lifetime
`REFRESH_TOKEN_EXPIRE_DAYS = 30` represents an absolute maximum session window established at login/registration. When a refresh token is rotated:
- A new refresh token is issued.
- `refresh_token_hash` is updated in place.
- `last_used_at` is updated to current UTC time.
- **`expires_at` is NOT extended**: Rolling extension is deliberately prevented so that continuous refreshes cannot keep a session alive indefinitely without re-authentication.

## 4. Concurrency & Refresh Token Rotation

### Row-Level Locking (`SELECT ... FOR UPDATE`)
Refresh operations execute within an atomic transaction with row-level locking:
```python
session = (
    db.query(AuthSession)
    .filter(AuthSession.refresh_token_hash == token_hash)
    .with_for_update()
    .first()
)
```

### Concurrency Policy
When two simultaneous refresh requests arrive with the identical refresh token:
1. **Request A** acquires the row lock on `auth_sessions`.
2. **Request B** blocks on the row lock.
3. **Request A** validates the session, generates a new token, updates `refresh_token_hash`, updates `last_used_at`, and commits.
4. **Request B** acquires the lock and re-evaluates. The original `token_hash` is no longer present on any active session; Request B immediately fails with a safe `AuthenticationError("Invalid or expired refresh token.")`.

### Bounded Replay Detection Policy (Known Phase 8 Limitation)
Under the single-row `auth_sessions` schema, rotating RT1 to RT2 replaces the stored hash in place. Consequently:
- A replayed, previously rotated RT1 fails because its hash no longer matches the database row.
- The server cannot distinguish a previously rotated RT1 from an arbitrary unknown token.
- **Architectural Boundary**: Full historical token-family replay detection (which requires retaining an immutable ledger of past tokens in a family to invalidate the active child upon old token replay) is deliberately deferred to preserve the single-table mandate of Phase 8.

## 5. Endpoints Contract

### 1. `POST /api/v1/auth/register`
- **Payload**: `name`, `email`, `phone`, `password`.
- **Normalization**:
  - Email: lowercase, trimmed whitespace.
  - Phone: canonical E.164 (`+919876543210`).
- **Role Assignment**: Server strictly assigns `CUSTOMER` role with `is_primary=True`. Client cannot specify roles or administrative flags.
- **Transaction Boundary**: Single atomic transaction creates User $\rightarrow$ assigns Role $\rightarrow$ creates AuthSession $\rightarrow$ returns tokens.
- **Race Condition**: Duplicate email/phone caught via database `IntegrityError` and returned as `409 CONFLICT_ERROR`.

### 2. `POST /api/v1/auth/login`
- **Payload**: `identifier` (email or phone), `password`.
- **Enumeration Protection**:
  Unknown email, unknown phone, incorrect password, inactive status, and suspended status all return the exact same generic error:
  ```json
  {
    "code": "AUTHENTICATION_ERROR",
    "message": "Invalid credentials.",
    "details": null
  }
  ```
  Internal logs distinguish safe event codes (`AUTH_INVALID_CREDENTIALS`, `AUTH_ACCOUNT_INACTIVE`, `AUTH_ACCOUNT_SUSPENDED`) without client leakage.

### 3. `POST /api/v1/auth/refresh`
- **Payload**: `refresh_token`.
- **Flow**: Validates session, verifies `revoked_at is None`, verifies `expires_at > now()`, checks user `status == "ACTIVE"`, rotates token hash, returns new access token and new refresh token.

### 4. `POST /api/v1/auth/logout`
- **Payload**: `refresh_token`.
- **Flow**: Sets `session.revoked_at = now()`. Safe and idempotent to call repeatedly.

### 5. `GET /api/v1/auth/me`
- **Header**: `Authorization: Bearer <access_token>`.
- **Flow**: Validates JWT signature/claims, verifies user status (`ACTIVE`), verifies underlying session is unrevoked, and returns sanitized `UserResponse`.

## 6. Raw Secret Redaction & Logging Policy

The following fields are strictly prohibited from logs, traces, exceptions, and serialized responses:
- Plaintext passwords
- Argon2id password hashes
- Raw refresh tokens
- Raw access tokens
- Full `Authorization` request headers

Safe logging records only:
- `request_id` (via `RequestIDMiddleware` and ContextVar)
- `user_id` and `session_id` (integers)
- Security event types (`AUTH_REGISTER_SUCCESS`, `AUTH_LOGIN_SUCCESS`, `AUTH_REFRESH_SUCCESS`, `AUTH_LOGOUT_SUCCESS`)
- Safe failure event codes (`AUTH_INVALID_CREDENTIALS`, `AUTH_ACCOUNT_INACTIVE`, etc.)
